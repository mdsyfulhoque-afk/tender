PART I — BACKGROUND AND OBJECTIVES
From a one-off seven-day product build to a reusable AI product engineering system.
1. Original Objective
The initial objective was to create one sellable digital product that could be shipped in seven days using only free tools and without paid APIs, paid hosting, or paid runtime services. The intended product direction combined the owner’s economics, policy, software/SaaS, financial-analysis and startup interests with a Bangladesh market context.
The early candidate was TenderToFit Lite: an offline-first tender support application for SMEs and procurement consultants. The proposed workflow was to import a tender, extract requirements, build a compliance matrix, identify missing evidence, calculate a readiness score, and export Word/Excel reports.
The discussion then established a more important strategic conclusion: software implementation is increasingly fast with AI, so the differentiator should be design quality, decision quality, evidence, workflow understanding, and reliable orchestration. The project therefore evolved from “build TenderToFit in seven days” into “build the engineering system that can repeatedly build TenderToFit and future products.”
2. Final Objectives
Create APES: a reusable AI Product Engineering System that converts an idea into a validated, specified, implemented, tested, packaged and learnable product through explicit artifact states.
Make the system self-bootstrapping in a fresh ChatGPT conversation through one Master Orchestrator prompt rather than requiring the user to issue a new prompt for every step.
Define work through capabilities, activities, tasks, artifacts, contracts, dependencies and quality gates instead of loose conversational roles.
Use TenderToFit as the pilot to validate the system and improve APES before generalizing it to other products.
Ensure the shipped product can operate without mandatory paid APIs, paid hosting or paid tools.
Make every important product decision traceable to evidence, assumptions, alternatives, review findings and acceptance tests.
Keep design and UX decisions ahead of implementation decisions; no feature should exist only because it is easy for an AI coding agent to generate.
3. Intended Users of This Document
The product owner approving strategic decisions and final gates.
ChatGPT or another high-reasoning AI acting as orchestrator, researcher, spec writer and reviewer.
Codex or another repository-level coding agent implementing bounded engineering tasks.
Human developers, analysts, designers, procurement specialists or consultants joining the project later.
Future APES instances used to build additional SaaS, policy, research, finance or software products.
4. Scope and Constraints
Constraint
Adopted requirement
Cost
No proposed runtime architecture may require paid APIs, paid hosting or paid development tools. Free/open-source/local components are the default.
Execution ownership
The AI system performs the operational research/specification/build-orchestration work; the owner primarily reviews strategic decisions and provides domain context when needed.
Evidence
No unverified market claim, competitor feature, pricing figure, legal statement or user complaint may be promoted to “fact” without source traceability.
Design
User journeys, decision points, information architecture and acceptance criteria must be defined before implementation tasks are issued.
Implementation
Coding work is decomposed into bounded tasks with explicit inputs, allowed files, tests and definition of done.
Quality
No artifact or task advances merely because content exists; it must pass its required gate.
Automation
The process should become state-aware and artifact-driven so prompts can be generated from system state rather than manually improvised.
5. Key Definitions
APES — AI Product Engineering System: the reusable operating system that governs research, design, engineering, QA, release and learning.
Capability — A stable ability APES must possess, defined independently from any particular model or tool.
Activity — A repeatable unit of work within a capability.
Task — An execution-sized unit with precise inputs, outputs, dependencies, owner/agent and definition of done.
Agent — An AI or human execution role defined primarily by the activities/tasks it performs and the artifacts it owns or reviews.
Artifact — A versioned, reviewable output that serves as a source of truth: e.g., evidence register, PRS, UX spec, architecture spec, code change, QA report.
Contract — The explicit preconditions, inputs, outputs, invariants and quality criteria governing a capability, agent, task or handoff.
Gate — A pass/fix/stop decision point that prevents unapproved material from flowing downstream.
Evidence — Source-backed information with provenance and confidence.
Assumption — A claim being used provisionally but not yet verified.
Decision — A recorded choice with alternatives, rationale, evidence and consequences.
State machine — The lifecycle controller that advances the project only when required artifacts and gates are satisfied.
PART II — APES FINAL ARCHITECTURE AND METHODOLOGY
A formal system for decision quality, traceability and repeatable product execution.
6. APES System Thesis
CORE PRINCIPLE
Optimize for decision quality, not document quantity. Artifacts exist to make decisions inspectable, testable, transferable and automatable. Conversation is temporary; durable project knowledge must become a versioned artifact or recorded decision.
APES is not a chatbot, a prompt library, or a conventional software-development checklist. It is an artifact-driven engineering operating system. Models, tools and prompts are replaceable implementations. Capabilities, contracts, state, evidence, quality gates and learning loops are the durable architecture.

8. Engineering Reasoning Framework
1.  Understand — define the actual decision/problem, user, context, constraints and unknowns before proposing a solution.
2.  Investigate — collect evidence, inspect files, research alternatives, identify contradictions and assign confidence.
3.  Design — develop user journeys, decision logic, information architecture and candidate solution patterns.
4.  Specify — convert the chosen design into explicit requirements, interfaces, data contracts, tests and bounded implementation tasks.
5.  Validate — test the artifact/implementation against evidence, acceptance criteria, consistency, security and business relevance.
6.  Improve — capture defects and lessons, update the decision record, revise the artifact or APES rule, and re-run the affected gate.

The executable backbone of APES.
14. Capability Engineering Rules
Capabilities are stable; agent/model/tool implementations may change without redefining the capability.
Every capability has a contract: purpose, inputs, preconditions, activities, outputs, metrics, risks, dependencies, consumers, review gate and completion criteria.
Activities are derived from capabilities; tasks are derived from activities; artifacts are produced/updated by tasks; agents are assigned to tasks.
No downstream capability may consume an artifact that has not passed the required quality gate.
When a real pilot reveals a gap, add or revise the minimal capability needed rather than introducing speculative architecture layers.

22. Master Orchestrator Prompt — Full-Control Version
PROMPT 00 — Master Orchestrator (Full-Control)
You are the AI Product Engineering System (APES) Master Orchestrator for [PROJECT NAME]. This prompt is self-contained: assume a fresh chat with no prior knowledge unless files or facts are explicitly provided.
MISSION
Build and govern a reusable product-engineering process first, then use it to deliver the product. APES must transform evidence into decisions, decisions into specifications, specifications into bounded implementation tasks, tasks into verified code/artifacts, and results into release and learning.
NON-NEGOTIABLE PRINCIPLES
1. Evidence before assumptions.
2. Research before product lock; design before implementation; verification before approval; commercial viability before release.
3. Artifacts, not conversation, are the source of truth. Material knowledge must become a versioned artifact, evidence item, assumption, decision or issue.
4. Define agents by activities/tasks, inputs, outputs, dependencies and quality contracts rather than prestige job titles.
5. Use state-machine logic and dependency-aware task connectivity. Do not advance downstream work until required gates pass.
6. Do not silently treat illustrative data, model guesses, prior assistant claims or unverified market statements as evidence.
7. When later decisions supersede earlier ones, record the supersession in the Decision Log.
8. Optimize for decision quality and user experience, not code volume or document volume.
9. The shipped product must not require paid APIs, paid hosting or paid runtime tools. Prefer local/open-source/no-incremental-cost components. Owner-side ChatGPT/Codex use is allowed but must not become a shipped runtime dependency.
10. Do not ask the user to perform operational work that the available AI/tooling can perform. Escalate only strategic decisions, missing permissions/files, irreducible domain ambiguity, or safety/legal issues.

41. Explainable Readiness Scoring — Illustrative Baseline
ILLUSTRATIVE FORMULA — NOT YET MARKET/DOMAIN VALIDATED
For reviewed requirements i, assign weight w_i and status value s_i: Compliant = 1.0; Partial = 0.5; Missing/Non-compliant = 0.0; Not Applicable = excluded. Numeric readiness = 100 × Σ(w_i × s_i) / Σ(w_i). If any requirement marked “mandatory disqualifying blocker” is Missing/Non-compliant, the overall decision label becomes NOT READY regardless of numeric score. The score is a navigation aid, not a legal determination.
The score must show its components. A user should be able to click a result and see which requirements and evidence items created it. Weighting defaults should be conservative and editable only through a governed configuration or user role, not hidden code.

57. APES Evolution Rules
No new architecture layer is added unless a real pilot or implementation failure demonstrates a gap.
Every APES change cites the triggering evidence/lesson and identifies affected capabilities, prompts, artifacts and gates.
A change that solves only a TenderToFit-specific problem remains a pilot extension unless generalized evidence supports promotion into core APES.
Prompt wording changes are versioned when they materially change agent behavior or output contracts.
Quality gates may become stricter after defects escape; they should not become looser merely to make progress appear faster.
Tool-specific dependencies stay in the implementation layer; the capability model should remain usable if ChatGPT, Codex or any specific model changes.
